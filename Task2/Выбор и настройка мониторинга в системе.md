# Задание 2. Мониторинг

## Мотивация

Рост нагрузки и участившиеся сбои в работе MES и CRM угрожают репутации и прибыли компании. Клиенты теряют доверие из-за просроченных заказов, а операторы сталкиваются с медленной работой системы, что напрямую влияет на мотивацию и эффективность.
Внедрение инструментов мониторинга позволит:

- Выявлять узкие места (например, рост нагрузки и увеличение продолжительности расчетов стоимости изделия).
- Предотвращать сбои до их влияния на клиентов.
- Оптимизировать нагрузку на API и MES, снижая риски потерь.

Без этого мы рискуем и дальше терять клиентов и контракты, а рост компании окажется под угрозой.

## Выбор подхода к мониторингу

Мы можем использовать подход USE для сервисов хранения данных:

- СУБД
- Object Storage

Для синхронных внешних API подойдёт метод RED:

- Shop API
- CRM API
- MES API

Для контроля внутренних асинхронных взаимодействий между сервисами можно использовать 4 золотых сигнала, т.к. добавляется параметр Saturation, под который подходит количество необработанных сообщений в очередях:

- RabbitMQ

### Пояснение

- Утилизация CPU и RAM (❗) - главный индикатор необходимости масштабирования или рефакторинга.
- Общий RPS, Latency, количество ошибок (❗) - показатель нагруженности системы, в связке с количеством ошибок и Latency может указывать на необходимость масштабирования при повышении нагрузки.
- Объём базы, файлов, необходимо дополнить текущими ограничениями, чтобы контролировать заполнение доступного места
- Количество сообщений в ожидании и в dlq кореллирует с количеством недовольных пользователей, не видящих изменений по своим заказам

## План действий

- Доработка сервисов для публикации необходимых метрик
- Публикация метрик на инстансах БД, RabbitMQ, S3 (с помощью эскпортеров, плагинов, или штатных средств)
- Разворачивание Prometheus и настройка сбора метрик
- Разворачивание Grafana, настройка источников данных, создание дашбордов
- Обучение команды сопровождения работы с дашбордами
- Возможна настройка отправки уведомлений по критическим показателям с помощью Grafana или Alert Manager

## Показатели насыщенности

- Количество синхронных запросов - если мы ожидаем минимальный поток RPS в режиме 24/7, то падение количества запросов до 0 или близко к этому может намекать на инцидент, даже при остуствии ошибок и без повышения Latency
- Процент ошибок в синхронных запросах - пороги необходимо установить опытным путём, но в критических ситуациях требуется подключение специалистов.
- Количество сообщений в ожидании в очередях - метрика прямо пропорцианальна количеству ожидающих клиентов
- Процент утилизации CPU/RAM/Disk_space/DB_size/S3_bucket - в случае 100% работа сервисов может быть парализована
